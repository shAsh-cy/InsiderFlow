# Performance — what is measured, and what was actually wrong

`pnpm lighthouse` is the committed runner. It samples each route `--runs`
times and judges the median, because these scores are a measurement of a
machine under load and not a property of the page.

`ANALYZE=1 pnpm --filter @insiderflow/web exec next build` adds source maps,
and `node scripts/analyze-chunks.mjs` then attributes every generated byte in
a chunk to the module it came from. That exists because two rounds in a row
guessed at a bundle's contents.

## The short version

| Round | Claim about `/screener` mobile             | Verdict                                                  |
| ----- | ------------------------------------------ | -------------------------------------------------------- |
| r4    | 76, "short of 90 for structural reasons"   | True, and the mobile/desktop labels were on it           |
| r16   | "nowhere near the claimed 100"             | **Wrong** — compared mobile against a desktop figure     |
| r17   | Regressed 76 → 62; 835ms in a 170 kB chunk | Half right. The score was low; the attribution was wrong |
| r18   | **82–84**, after removing a layout shift   | Measured, with the cause named and the fix attributed    |

## r17's attribution was wrong, and this is how

r17 reported 835ms of script evaluation in one 170 kB chunk and wrote down
the hypothesis it could not test: TanStack Table plus TanStack Virtual. It
labelled it a hypothesis. It was wrong twice over.

Built with source maps, chunk `6121` is **Next's own App Router client
runtime** — 43.7 kB of `next` plus `app-router.tsx`, `layout-router.tsx` and
the whole `router-reducer/` tree. There is no TanStack in it. And a Next
runtime chunk is loaded by **every** route, so it cannot be what makes
`/screener` differ from `/trades`.

What `/screener` actually carried beyond `/trades` was 208 kB across six
chunks:

| Module                           |    Bytes | Share of the screener-only payload |
| -------------------------------- | -------: | ---------------------------------- |
| `motion-dom`                     |  92.4 kB | 44%                                |
| `framer-motion`                  |  19.5 kB | 9%                                 |
| motion internals                 | ~16.3 kB | 8%                                 |
| `@tanstack/table-core`           |  48.6 kB | 23%                                |
| `@tanstack/react-table`          |   0.7 kB | —                                  |
| domain components, dialog, icons |   ~30 kB | 15%                                |

TanStack is real and second. **TanStack Virtual does not appear at all** —
half the guess was for a library the route does not load.

## Why motion was there: a barrel

`/screener` → `screener-results.tsx` → `TradeTable` → `import { … } from
"@/components/domain"`. That barrel re-exports `StatCard` and `LiveFeedRow`,
and both import `motion/react`. `TradeTable` renders neither. Importing the
barrel for eight of its exports pulled the animation engine into every route
that renders a trade table: `/screener`, `/insider/[id]`, `/stock/[ticker]`.

`/trades` reaches for `StaticFeedRow` by deep import, never touches the
barrel, and carries no motion chunk — which is exactly why it scored 88 while
`/screener` scored 62.

Fixed by importing the eight components directly. `/design` still imports the
barrel and should: it renders every primitive. **A barrel is only a hazard
where the importer wants a few of its exports and the unused ones are heavy.**

Measured, deterministic, no Lighthouse involved:

|                                 | before |      after |
| ------------------------------- | -----: | ---------: |
| `/screener` First Load JS       | 286 kB | **239 kB** |
| `/screener` total route payload | 920 kB | **776 kB** |

## The bimodality was layout shift, and it was most of the score

This is the part r17 could not see, because it never captured CLS.

`/screener` swung between two states on an unchanging build. Not a
distribution — two modes:

| CLS   | CLS sub-score | performance |
| ----- | ------------- | ----------- |
| 0.001 | 100           | 77–78       |
| 0.409 | 24            | 61–63       |
| 0.488 | 17            | 57–61       |

CLS is **25% of the mobile performance score**. A CLS sub-score of 17 against
100 is ~21 points of the total, which is the whole swing. `/trades` measured
CLS 0.001–0.002 on every run and scored 85–93.

Lighthouse 12 reports the number without a subject — it emits no
`layout-shift-elements` audit in this build — so the elements came from the
browser's own `layout-shift` PerformanceEntry `sources`, under mobile
emulation with 4× CPU throttling.

Two insertions above the results, in every shifting run:

```
shift 0.080 @~1.5s   everything below y=302 moves down 124px
shift 0.408 @~2.5s   everything below y=186 moves down  86px
                     AND  div.flex.justify-center  364x30@758 -> 0x0@0
```

- **86px** is the `AccessBanner` — 62px of banner plus a 24px gap. It started
  hidden and appeared in a `useEffect` after mount.
- **124px** is the `FilterBar`, which sits inside a `<Suspense>` **with no
  fallback**, so it occupies nothing until it resolves.
- The **758px** figure is what makes the second shift 0.408 rather than the
  0.104 an 86px move could produce on its own: a 30px element at the bottom of
  the viewport is removed in the same frame, and a removed node scores as a
  displacement to the origin. Distance fraction 758/823 = 0.92.

### Why `/screener` and not `/trades`, when both render the banner

Both pages render `AccessBanner`. Only `/screener` shifted. The difference is
**when hydration finishes relative to first paint**: `/screener` was 286 kB of
First Load JS against `/trades`' 228 kB, so its mount-time insertion landed
after paint often enough to count. On the runs where hydration won the race,
CLS was 0.001 and the score was 77.

That is also the mechanism behind the bimodality itself. It was never a
"lazy chunk sometimes warm" — it was a race, and the score recorded which
side won.

## The fix, and what it moved

`AccessBanner`'s dismissal was already stored in a **cookie**. Its own comment
defended the mount-time render against the only alternative it had considered
— rendering server-side unconditionally and hiding on the client, which does
flash the banner at everyone who dismissed it. A cookie is the thing a server
can read; it simply was not being read there. The page now reads it and passes
`dismissed` in, so the first paint is already correct: no flash, no insertion.

Measured on the same machine, same build pipeline, medians of 5–6:

|                                |                       before |              after |
| ------------------------------ | ---------------------------: | -----------------: |
| `/screener` performance median |                           76 |          **82–84** |
| run-to-run spread              |            57–81 (24 points) | 80–85 (2–5 points) |
| CLS                            | 0.409–0.488 on shifting runs |     ≤0.006 typical |

Two sweeps of 5, on the same machine an hour apart, medianed 84 and 82. Both
are quoted rather than the better one: the second sweep also moved `/` 79→81
and `/design` 70→67, which is the machine drifting, not the pages.

Against r17's reported 62, that is +22. Against a like-for-like re-measurement
on a quiet machine today, +8 — and the spread collapsing is the more
important half, because a 24-point band is wider than any regression this
gate is meant to catch.

### What the bundle fix contributed on its own: not resolvable

Honesty about attribution, since that is this document's whole subject. The
barrel fix was measured **alone**, before the CLS cause was known: median 64
across `64 64 64 77 81`. The pre-fix median that day was 76 across
`57 60 76 76 81`. Both samples sit inside the same CLS-driven noise band, so
**no Lighthouse effect can be attributed to the barrel fix from that data**,
in either direction.

It is kept because 47 kB of First Load JS is a real, deterministic reduction
that no sampling is required to observe, and because less JavaScript means
hydration finishes earlier — which is the race the CLS fix also addresses.
But this document is not going to claim Lighthouse points it did not measure.

## Current standing, and what is still short

`pnpm lighthouse --runs=5`, quiet machine, mobile preset:

| Route           | sweep 1 | sweep 2 | spread (both) | goal | floor |
| --------------- | ------: | ------: | ------------- | ---: | ----: |
| `/`             |      79 |      81 | 71–81         |   90 |    72 |
| `/trades`       |      86 |      87 | 83–90         |   90 |    82 |
| `/screener`     |  **84** |  **82** | 80–85         |   90 |    78 |
| `/stock/ZZNOVA` |      73 |      71 | 69–73         |   90 |    65 |
| `/design`       |      70 |      67 | 63–73         |   85 |    66 |

Every route is still short of the goal and the runner prints that deficit on
every run. The goal stays at **90** — the number the original brief set for
this preset — and no threshold has been moved to meet a measurement.

Only `/screener`'s floor moved, 55 → 78. The other four are untouched: this
round did not measure an improvement on them, and a floor raised on noise is
a false red waiting to happen.

### Not fixed, and named

- **The `FilterBar` Suspense boundary still has no fallback**, so the 124px
  insertion is still there. It is the smaller of the two shifts (0.080) and
  reserving its height correctly needs the collapsed and expanded heights at
  each breakpoint, which is a layout change rather than a one-line fix.
- **The 30px element removed at the viewport bottom** —
  `screener-results.tsx`'s centred "Load more" / "End of results" row — is
  what turns an 86px move into a 0.408 shift. With the banner no longer
  inserting, it no longer has a large move to amplify, and the measured CLS
  is ≤0.006. The removal itself was not chased further.
- **`/stock/ZZNOVA` at 71–73 and `/design` at 67–70** have not been diagnosed
  at all. `/design` renders every primitive plus a 10k-row virtualised table
  by design; `/stock` has not been looked at. Note that `/design`'s second
  sweep medianed 67 against a floor of 66 — one point of headroom. That floor
  was set in r17 from a median of 72, so either the page has drifted or the
  machine has. It is flagged rather than moved: lowering a floor to make room
  for a drop is how a regression stops being reported, and it has not been
  established which of the two this is.

## Reproducing

```bash
pnpm --filter @insiderflow/web exec next build
pnpm --filter @insiderflow/web exec next start -p 3100 &
pnpm lighthouse --runs=5                 # mobile, the gate
pnpm lighthouse --runs=5 --preset=desktop

# chunk composition
ANALYZE=1 pnpm --filter @insiderflow/web exec next build
node scripts/analyze-chunks.mjs --top=14
node scripts/analyze-chunks.mjs 6121
```

Kill stray Chrome processes first. r4 lost a sweep to twenty-one of them and
r16 lost one to a concurrent `next build` — this suite's recurring lesson is
that the test measures the machine unless you make it not.
